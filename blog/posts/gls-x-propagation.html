GLS 时序检查中的 X 传播：一个没有统一标准的角落

门级网表的 X 从哪来、SDF 反标如何制造新的不定态， 以及三种处理策略对签核结论的实际影响。标准把这里留成了空白，空白就只能由工程师自己定义。

2026-09-06 · 9 分钟阅读 · GLS / XProp / 逻辑仿真

门级仿真的时序检查报告里出现 X，是几乎每次都会碰到的事。麻烦的地方在于， 同一个 X 在两种语境下的含义完全不同：它可能是设计里真实存在的不定态， 也可能只是仿真器还没算出一个确定值。这两者混在一份报告里，签核结论就没法直接用了。

这篇文章整理我对这个问题的理解。核心结论先放在前面： IEEE 标准定义了 X 的逻辑语义，也定义了 SDF 的格式，但没有定义"当数据信号为 X 时， setup / hold 检查应该报违例还是放过"。这个空白是所有不一致的根源。

一、门级网表的 X 从哪里来

RTL 层的 X 来源是好数的：未初始化寄存器、带 x / z 字面量的赋值、 不完整的 case、多驱动线网。门级网表在这方面是 RTL 的超集，而且加了几类新的：

  • 大面积的未初始化触发器。门级网表通常不保证复位覆盖到每一级。 扫描链插入后，大量触发器的上电值是 X —— 在 RTL 仿真里你可能看不到， 因为 RTL 层的复位建模通常比综合后的网表"干净"。
  • 多驱动与总线冲突。综合与 DFT 插入后出现的三态网络， 当两个驱动同时使能时，仿真器会给 X（或者给一个强驱动值，取决于建模）。这本身是真实缺陷， 但它出现的位置往往在测试逻辑里，容易被当成噪声忽略。
  • 亚稳态与跨时钟域采样。仿真器对建立/保持违例的处理方式， 决定了采样时刻附近的值是否被建模为 X。
  • SDF 反标引入的不确定性。这是门级独有的一类。SDF 里的延迟来自库特征化， 不同 corner 的数值不同；更重要的是，SDF 里没有覆盖到的路径会用工具默认值或零延迟 —— 一个被反标成零延迟的组合路径，在时序检查看来就是一个不存在的路径。

还有第五类，也是我觉得最容易被忽视的一类：

时序违例会自己制造 X。当某个触发器发生 setup 违例，它的输出在仿真器里 可能被建模为 X —— 因为仿真器无法确定它究竟是旧值还是新值。 而这个 X 会继续往下游传播，触发下游的时序检查。于是一条真实违例， 在下游表现为一串 X 相关的检查失败。

这就带来一个级联效应：报告里最后看到的失败条目，未必是最初那条违例造成的。 顺着报告从上往下读，通常读不到根因，因为报告是按信号层级排的，不是按因果排的。

二、三种处理策略，以及它们各自的代价

X-pessimistic：保守到底

规则很简单：只要参与运算的任何一个输入是 X，输出就是 X，只有少数能确定的情况例外 （X & 0 = 0，X | 1 = 1）。违反的路径就是违例。

好处是不会漏掉真违例。坏处是 X 会像野火一样扩散： 一个未初始化的触发器足以让下游几十个信号全部变成 X，报告里几百条"违例"里可能只有一条是真的。 噪声比高到一定程度后，报告就失去可读性了。

X-optimistic：假设 X 是"任意值"

仿真器在能确定最终结果时就不再输出 X。除了上面的两条吸收律， 还包括对条件语句的处理 —— if (x) A else B 如果 A 和 B 的取值恰好相同， 就认为结果确定；以及位选择、拼接等运算里的进一步简化。

好处是报告干净、仿真快。坏处是它会掩掉真违例： 一个实际上因为未初始化而行为不确定的设计，在 optimistic 语义下可能"跑通了"。 这是最危险的一类假阴性 —— 你拿到一个绿色报告，但它是假的。

精确传播：按真值表走，但时序检查那一层依然没定义

更细的 X 传播算法（业内常说的 X-accuracy）会维护更精确的 X 语义， 减少无意义的扩散，同时保住不确定性。这解决的是传播这一层的问题。

但它解决不了检查这一层的问题。原因很直接： 传播的语义有 IEEE 真值表可依，而检查的语义没有。 当数据端的值是 X，这个检查到底算不算失败 —— 标准里查不到答案，因为标准压根没写。

三、为什么标准没写

我的理解是，这不是遗漏，而是有意回避。X 在时序检查的语境里同时承担了两个角色： 它可能是真实的设计缺陷（该初始化而没初始化、真实的竞争）， 也可能是仿真噪声（尚未求值、建模不完整）。

标准委员会没法替用户决定取哪一边 —— 因为正确答案取决于你在流程的哪个阶段、 你要回答什么问题。在早期功能调试阶段，你需要低噪声；在签核阶段，你需要零漏报。 这两个需求在语义上是矛盾的。

结果就是工具各自为政。同一个设计、同一套 SDF，在不同仿真器上跑出的时序检查报告 可以有很大的条目差异，而这个差异不反映设计质量，只反映语义选择。

四、三种策略的对签核影响，摆在一起看

策略真违例漏报假违例噪声仿真代价适合的阶段
X-pessimistic 低 很高 中 签核前的最终检查
X-optimistic 高（危险） 很低 低 功能调试、回归
精确传播 中 中 高 根因定位

这张表里没有"最好"的一列。选择哪一行，取决于你此刻要靠报告回答什么问题。 把策略当成一个可以切换的开关，而不是一个固定的正确配置， 这是我在实际工作里得到的最有用的一条经验。

五、工程上比较务实的四件事

1. 做一次 X 来源审计

在读时序检查报告之前，先统计 X 的来源分布：多少来自未初始化触发器、多少来自多驱动、 多少来自 SDF 未覆盖路径。这一步做完，往往能直接消掉一大半 X —— 比如补齐复位遍历、给扫描链加初始化、修掉综合产生的多驱动。 能消掉的 X 就不用讨论了，剩下的才是真问题。

2. 报告分级，而不是一张清单

把"X 传播导致的检查失败"和"数值上真实越界的检查失败"分成两个区。 前者需要你先解决 X 来源，后者才是可以直接行动的。混在一张清单里， 工程师的注意力会被随机分配。

3. 给 X 标来源链

每条 X 相关的失败上，附一条"这个 X 最初从哪里来"的链路 —— 追到未初始化触发器、追到多驱动、或者追到某条 setup 违例。 这条链是解决级联问题最有效的工具。实现上不难，难的是仿真器要在内部保留这部分元数据。

4. 按阶段切换策略

功能回归用 optimistic 跑速度，签核用 pessimistic 跑覆盖率，根因定位用精确传播。 前提是你知道自己在哪个阶段，并且把当前策略记录在报告里。 一份不说明 X 语义的时序报告，跨团队传递时几乎必然被误读。

六、一个我认为还没被解决的问题

回到最根本的问法：X 态在时序检查中的"正确语义"应该是什么？

我认为需要同时满足三个约束，而这三个约束在现有工具里没有被同时满足：

  • 物理真实性 —— 报告反映的是设计在硅上的行为，不是仿真器的求值顺序。
  • 可解释性 —— 每条失败都能回溯到具体来源，而不是一个 X 的涟漪。
  • 计算代价 —— 精确传播的代价必须可控，否则签核跑不完。

目前没有公认的答案。规则是使用者定的，但得有人先把定义写清楚， 才能谈不同工具之间的一致性。这也是我认为门级场景下的 X 传播处理值得投入的原因： 标准空着的地方，先给出清晰定义的那一方会获得解释权。
